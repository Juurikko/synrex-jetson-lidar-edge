A few engineering details behind this:

I used a trained, compact seven-class 3D U-Net, exported through ONNX and built into a target-specific TensorRT FP16 plan through NVIDIA’s public APIs. The native runtime keeps the engine, execution context, CUDA stream and buffers alive across windows. Python/PyTorch support training and offline tools; they are absent from production inference. I wrote the original native integration and streaming implementation with OpenAI Codex assisting coding, testing and verification under my specifications and review; the U-Net architecture and external libraries retain their own attribution.

The hard work extends beyond the network: CPU spatial grouping and deterministic feature preparation, CUDA inference and reconstruction back to original source-point identities, bounded queues, versioned binary TCP framing, independent subscriber validation, and incremental map upserts/eviction. Each counted point gets a fresh neural prediction; the map never supplies cached inference labels. “Map updates” in these tests count accepted observations, including reobservations—not newly discovered unique cells. A bounded last-observation map is not SLAM, probabilistic semantic fusion or a survey reconstruction.

I keep measurement boundaries separate. The ~2M/s scene-A result covers two qualified 60-second external TCP replay trials through validated output and map observations. Dense scene C and full churn qualify at ~1.5M/s; harder 2M/s trials retain their FAIL receipts. The ten-minute full-churn run averages ~999,981 fresh points/s, with 39.845888 ms p99. These numbers are neither network ingress alone nor neural kernel throughput. Optional asynchronous first-observation LAZ export and offline COPC conversion have separate correctness checks; export is not included in those headline throughput qualifications. The short JSON media recording’s 274.478 ms p99 FAIL is retained separately and is never a latency-performance citation.

For a UAV, “onboard” remains a hypothesis. An end-to-end port would need measured energy/power, GPU and memory bandwidth, CPU geometry capacity, stream transport and sensor bandwidth, battery/thermal testing, model accuracy and complete hardware qualification. Real georeferencing also needs calibrated positioning, SLAM or GNSS/IMU integration as appropriate, motion compensation and sensor synchronisation. None of that is established by a desktop replay. Inspection, change detection, obstacle/context perception and exporting useful data before landing are development opportunities, not demonstrated flight capabilities or safety guarantees.

NVIDIA’s [Jetson module lineup](https://developer.nvidia.com/embedded/jetson-modules/) and [embedded platform overview](https://www.nvidia.com/en-us/autonomous-machines/embedded-systems/) provide hardware context only. I make no point/s prediction for Jetson AGX Thor / Jetson Thor or Jetson AGX Orin. Advertised FP4 sparse TFLOPS and INT8 TOPS do not predict this small FP16 model’s CPU/memory/transport-heavy pipeline throughput.
